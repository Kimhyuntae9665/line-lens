# 검증 범위와 재현 방법

검수일은 2026-10-09(KST)입니다. 실제 Qwen 추론, 시뮬레이터 계산, 모의 응답을 사용하는 자동 테스트를 각각 구분합니다. 전부 합성 생산라인의 소프트웨어 검수이며 실제 제조 현장의 개선 효과나 안전성을 검증한 결과는 아닙니다.

## 1. 자동 테스트

```bash
npm test
```

공개 직전 Node.js 22.22.2에서 **40개 모두 통과**했습니다. GitHub Actions는 Node.js 24에서 같은 명령을 실행합니다. 수량 보존, 버퍼 한도, 반복 재현, 동일 난수 조건, 휴식 중 작업 정지·피로 회복, 인원에 맞는 인시 분모, 후보 제약과 캐시, 잘못된 입력을 확인합니다.

LLM 서비스 테스트는 의도적으로 모의 `/models`·구조화 응답을 사용합니다. 실제 모델 없이도 잘못된 후보 ID, 근거 문장, `null`·배열·문자열·숫자인 근거 항목, 미확인 목표, 연결 실패를 재현합니다. 잘못된 근거 항목은 `502 / LLM_INVALID_CANDIDATE`와 모델 오류 메타데이터를 보존합니다. **자동 테스트 40개 통과를 실제 LLM 추론 40번 성공으로 읽지 않습니다.**

## 2. 모델 없이 계산 결과 재현하기

```bash
npm run benchmark:advisor
# 파일로도 저장하려면:
npm run benchmark:advisor -- --out report.json
```

이 명령에는 모델 서버가 필요 없습니다. `llmCalled:false`와 `SYNTHETIC_SIMULATION`을 출력합니다. 기준은 FLEX·난수 조건 20261007·작업자 모델 켜짐·수작업 공정별 2명·속도 100%·90분마다 5분 휴식입니다. 목표는 양품 1,000켤레, 최소 양품률 95%, 공정 변경 최대 3개, 가정 피로 40·작업부하 90% 이하, 작업자 조건 변경 허용입니다.

| 재현할 항목 | 결과 |
|---|---:|
| 비교한 설정 | 504개 |
| 전체 제약을 만족한 설정 | 288개 |
| 가정 부담 한도 제외 | 216개 |
| 품질 한도 제외 | 0개 |
| 요청 당시 기준의 목표 도달 | 409분 |
| 더 빠르게 | 345분 / 양품 1,396 / 15명 |
| 더 적게 바꾸기 | 400분 / 양품 1,225 / 12명 |
| 작업 부담 줄이기 | 407분 / 양품 1,201 / 15명 |

공개 직전의 한 번의 실행은 새 계산 2,585.18ms, 같은 설정의 캐시 응답 8.81ms였습니다. 실행할 때마다 시간을 새로 측정합니다. CPU 부하·런타임에 따라 시간은 달라져도 같은 코드·설정에서 후보 수치가 재현되는지 확인합니다. 캐시 응답의 504는 비교한 설정 수이며 새로 504번 계산한 뜻이 아닙니다.

## 3. 실제 로컬 모델로 확인한 두 실행

CPU·llama.cpp·Qwen3-4B-Q4_K_M을 사용했습니다. [연결 방법](local-ai-setup.md)에 따라 두 서버를 실행해야 합니다. 단순 모델 목록 조회에 그치지 않고 **목표 해석과 후보 설명 두 단계의 실제 추론**을 확인했습니다.

입력: `직원들이 무리하지 않으면서 양품 1,000켤레를 더 빨리 만들고 싶어`

수량은 요청문에서 읽고, 요청에 없는 양품률·피로·부하·변경 제한은 시스템 기본값으로 표시합니다. 사용자가 이를 확인한 뒤에 계산을 실행했습니다.

| 단계 | 포트폴리오 제작 당시 관찰 | 공개 직전 재검수 |
|---|---:|---:|
| 시뮬레이터 새 계산 | 4.86초 | 2.61초 |
| 실제 LLM 목표 해석 | 34.74초 | 20.73초 |
| 실제 LLM 후보·허용 근거 선택 | 63.32초 | 45.35초 |
| LLM 두 처리 시간 합계 | 98.06초 | 66.08초 |

각각 한 번의 관찰이며 평균·최적·보장 응답 시간이 아닙니다. 표의 시간은 UI의 소수 둘째 자리 표시값입니다. LLM 합계에서 시뮬레이터 시간과 사용자의 확인·클릭 대기를 제외했습니다. 두 실행의 504개·288개·216개 및 후보 생산 수치는 같았습니다.

- 제작 당시 전체 실행 근거: [worker-ai-observed-run.json](../experiments/worker-ai-observed-run.json). `advisor.interpretation`, `advisor.result`, `advisor.appliedCandidateId`에 실제 결과·시간·적용 후보가 있습니다. 원본 모델 서버의 토큰 스트림을 보존한 파일은 아닙니다.
- 공개 직전 DOM 관찰 기록: [worker-ai-publish-check.json](../experiments/worker-ai-publish-check.json). 실제 화면에서 읽은 수치와 반영된 조작값을 기록했으며 제공자 원시 응답과 구분합니다.
- 제작 당시 실제 화면: [AI 목표·조건·후보](screenshots/11-worker-ai-advisor.jpg), [공장 적용 화면](screenshots/09-worker-factory.jpg), [휴식 상태](screenshots/12-worker-rest.jpg).

빠른 후보 적용 버튼을 누른 뒤 자재 감축 60%·성형 감축 25%·검사 강화 켜짐·공정별 3명·속도 100%·90분마다 5분 휴식이 사이드바에 반영됐습니다. 개선 라인의 총 생산 1,430·양품 1,396·인원 15명도 확인했습니다. 요청·비교 단계만으로는 공장 설정이 바뀌지 않았고, 적용 후 재생 시점이 유지됐습니다.

`질문·결과 초기화`는 질문과 AI 결과를 지우면서 적용한 공장 설정을 유지했습니다. `처음부터 재생`은 시점을 0으로 되돌렸습니다. 모델 서버를 종료한 뒤 연결 오류 안내가 나타나고 수동 생산라인 조작이 계속 가능한 것도 확인했습니다.

## 4. 무엇까지 확인했는가

현재 모델의 공정 시간, 작업 비중, 피로 회복 계수와 비교 한도는 가정값입니다. 입력을 바꾸면 실제 계산이 바뀌지만 회사의 실제 생산을 예측하는 모형으로 보정되지는 않았습니다. 실제 적용에는 정지 코드 정의, 처리시간·수작업 비중·인력 배치·휴식 기록을 수집하고 같은 조건에서 현장 결과와 대조해야 합니다.

로컬 LLM은 이 가정의 타당성을 입증하거나 사고 확률을 계산하지 않습니다. [AI 처리 상세](ai-workflow.md), [작업자 모델](human-factors-model.md), [API 계약](advisor-api.md)을 함께 읽어 주세요.
